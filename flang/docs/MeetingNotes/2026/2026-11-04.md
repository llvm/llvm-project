* Design docs and/or RFCs
  * [\[RFC\] Enabling bulk transfer for endian-converted unformatted I/O](https://discourse.llvm.org/t/rfc-enabling-bulk-transfer-for-endian-converted-unformatted-i-o/92581)
    * Related PR: [https\://github.com/llvm/llvm-project/pull/236692](https://github.com/llvm/llvm-project/pull/236692)
    * No update on the call, continue discussion on the PR
  * [\[RFC\] A directive to set the alignment of variables in flang](https://discourse.llvm.org/t/rfc-a-directive-to-set-the-alignment-of-variables-in-flang/92619)
    * Related Draft PR: [https\://github.com/llvm/llvm-project/pull/236444](https://github.com/llvm/llvm-project/pull/236444)
    * Related RFC from March: [\[RFC\] Alignment of global arrays](https://discourse.llvm.org/t/rfc-alignment-of-global-arrays/90397/14)
    * Whether to support Intel’s old format or not?
      * There are codes that use this, so supporting it would be good
    * What is the highest alignment to support?
      * Intel has support for hugepages, should we use that value as well?
      * Default suggested is 2^21
      * Gfortran may end up implementing something similar to what this RFC decides
        * Do we have a contact in the Gfortran community we can reach out to for coordination purposes?
        * What about IBM’s xlf?
    * Common block alignment?
      * Intel warns but ignores.  Do we want to be able to align the beginning of a common block?
      * Do they allow members of a common block to have their own alignment?
      * Agree to disallow alignment of members of common blocks, allow alignment of common blocks themselves
      * Will make this a separate PR from the alignment of other things
      * If we make a change, this will break compatibility and require much recompilation or relinking
  * [Should flang limit the number of nested parenthesis?](https://discourse.llvm.org/t/should-flang-limit-the-number-of-nested-parenthesis/92656)
    * Related Issue: [https\://github.com/llvm/llvm-project/issues/236881](https://github.com/llvm/llvm-project/issues/236881)
    * It is possible to stack overflow the parser without the limit being present
    * Propose including a stack overflow signal handler (more general solution than just handling the parentheses)
    * What about the stack trace signal handler that LLVM already has?
  * [\[RFC\] Typedefs for evaluate::Type\<TypeCategory::CAT\>](https://discourse.llvm.org/t/rfc-type-aliases-for-evaluate-type-typecategory-cat/92722)
